## Context

见 `proposal.md` 的问题说明。当前宫格构建器把首格写成首分镜开场，后续格写成“前一分镜 `video_prompt.action`，过渡到后一分镜 `image_prompt`”；一张静态图因而承载多个时间点。角色引用则由通用编号器把 `@[名称]` 直接替换成“图N”，项目 `characters` 中的描述和逐分镜角色名单没有进入宫格提示词。

宫格提示词在 HTTP 路由、媒体工具和正式任务执行三个入口构建。正式任务会在后端参考图上限确定后重新构建并覆盖记录。正式产物的视觉依据当前也投影了前一分镜视频动作，因此本次不能只改字符串模板，否则产物新鲜度判定会与真实生成输入分叉。

## Goals / Non-Goals

**Goals:**

- 保持画格与分镜一一对应，同时让每格只表达该分镜 `image_prompt` 的一个静态状态。
- 用一个确定性的角色身份投影同时驱动提示词和视觉依据。
- 在不调用额外模型的前提下，利用已有角色名单、项目描述和参考图编号约束同框人物。
- 保持创建阶段无参考编号的预提示词与执行阶段有实际编号的正式提示词语义兼容。

**Non-Goals:**

- 不拆分或裁切“人脸特写＋三视图”角色资产，不改变参考图选择与发送上限。
- 不自动改写已有分镜 `image_prompt`，也不从自然语言猜测未明确写出的左右、前后位置。
- 不承诺生成模型绝不违约，也不增加成图人物识别或自动重试。
- 不改变宫格布局、切格回填、REST API 或项目 JSON schema。

## Decisions

### 1. 画格直接投影同序分镜的图像提示词

内容格 `i` 只渲染 `scenes[i].image_prompt`。格0仍标为首分镜开场；后续格可保留“前一分镜→当前分镜共享帧”的帧链含义，但正文只描述当前分镜的开场静态状态，不再读取前一分镜 `video_prompt.action`。

这与切格后按 `next_scene_id` 回填当前分镜头帧的现有映射一致，也修正了代码注释声称“末格是末分镜开场”而实现仍拼接过渡动作的不一致。

备选方案是继续拼接动作，再要求模型“只画动作完成态”。该方案仍把多个时态交给模型消歧，不能消除重复人物的结构性来源，因此不采用。

### 2. 建立确定性的宫格角色身份投影

新增一个纯数据投影，输入为：

- 本宫格的同序分镜；
- 当前剧本骨架的角色名单字段名；
- 项目 `characters`；
- 本次提示词实际可用的参考图槽位。

投影输出包含全局角色身份表和逐格角色名单。角色按首次出镜顺序稳定排列；资产名沿用现有规范化与衍生角色解析规则。普通角色取自身 `description`；衍生角色同时保留本体描述和衍生描述。缺失或类型错误的数据降级为空描述，不臆造外貌。

全局 `【角色身份】` 段只写一次完整描述，避免逐格重复拉长 prompt。角色参考图实际存在时写成“子墨（图1）”；没有实际槽位时只写“子墨”。场景、道具等非角色 mention 继续使用现有图N渲染。

备选方案是用文本模型从角色描述抽取“核心视觉特征”。它会引入额外调用、非确定性和新的缓存/失败路径；项目中的 `description` 已是角色视觉定义，因此直接使用原文。

### 3. 逐格角色清单使用正向唯一性约束

每个内容格在画面正文前增加简短的角色清单：

- 无角色：不输出角色清单；
- 单角色：`本格角色：子墨（图1）1人`；
- 多角色：逐一列出，声明每个角色各1人、身份和外观分别遵循全局身份表。

多角色格再声明角色之间不得复制、融合、替换或交换身份。身份差异来自全局项目描述；空间位置仅由原始 `image_prompt` 提供并原样保留，不做自然语言抽取或推断。这样既覆盖“两个骆宾王”和“一个子墨被复制”，又避免系统无依据地指定站位。

只在末尾增加“不要重复人物”的备选方案不采用，因为它没有告诉模型该出现谁、各出现几人以及如何区分。

### 4. 宫格专用 mention 渲染保留角色名称

通用参考图编号仍用于声明和非角色引用。宫格角色 mention 使用身份投影渲染为“角色名（图N）”，而不是只剩“图N”。该变化限定在宫格路径，避免影响普通分镜图和参考生视频既有契约。

没有被实际发送的角色参考图不得产生虚构编号；此时 mention 退化为角色名，并由全局身份描述继续提供约束。

### 5. 正式视觉依据升级并移除视频动作依赖

宫格视觉依据升级 kind version，并把每格的规范化 `image_prompt`、角色名单及所引用角色的规范化描述纳入输入；不再投影 `video_prompt.action`。因此：

- 修改角色描述会使相关宫格变旧；
- 修改该格角色名单会使宫格变旧；
- 只修改视频动作不会使静态宫格变旧。

执行任务和产物补录规划器必须调用同一个身份投影，避免新鲜度判定分叉。参考图证据继续沿用现有完整装配集策略；图N只属于供应商提示词，不进入稳定视觉依据。

kind version 升级会让旧宫格按新语义被识别为需要重新生成，这是目标定义变化的预期结果，而不是项目数据迁移。

### 6. 三个构建入口共享完整上下文

HTTP 路由、媒体工具和正式执行器都向宫格构建器传入 `char_field` 与项目角色表。创建阶段尚无最终后端与参考图槽位时，先生成不带图N、但带角色名称和描述的预提示词；正式执行阶段在参考图裁剪后重新生成带准确图N的提示词并覆盖宫格记录。

正式提示词仍是执行时实时输入，不信任队列中保存的旧 prompt。视觉依据与正式提示词在同一执行快照中构建。

## Risks / Trade-offs

- [完整角色描述会增加提示词长度] → 全局描述只写一次，逐格只写名称、编号和数量；不重复描述全文。
- [项目角色描述可能混有“需补充”等非视觉文本] → 保持确定性并忠实使用项目数据；本变更不引入启发式摘要，后续可另行改善角色资料质量。
- [角色名单与图像正文可能不一致] → 角色名单作为身份与数量真相源，正文作为构图真相源；现有数据校验继续负责引用完整性，本变更不静默增加或删除角色。
- [模型仍可能忽略数量或身份约束] → 用正向清单、参考绑定和差异描述降低概率；成图检测与自动重试留作后续能力。
- [视觉依据版本升级使存量宫格显示过期] → 保留文件和记录可读，仅在用户需要新语义时重新生成。

## Migration Plan

1. 部署新提示词与视觉依据逻辑，不迁移项目 JSON 或宫格记录。
2. 现有宫格图片继续可查看；新鲜度检查按升级后的目标依据将旧产物标记为需重新生成。
3. 新建或重新生成的宫格写入单时态、角色绑定后的正式提示词。
4. 回滚时恢复旧提示词与旧视觉依据版本；新版本产物文件仍可读，但按旧目标依据可能被判定为需重新生成。
